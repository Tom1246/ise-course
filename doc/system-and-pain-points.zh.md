# 系统、流程与痛点（问题界定）

> **这份文档的定位**：中文工作文档，不是提交件。它的作用是先把"这个系统是干什么的、流程怎样、痛在哪"讲清楚，
> A1 正文（`doc/assignments/A1-brief-en-2026-09-28.md`，英文）的第 2、3 节就是在它基础上写的。所有数字都由 `scripts/` 里的脚本生成，
> 原始输出在各来源目录下（`data/s1-plan-workbook/`、`data/s2-public-listing/`、`data/s3-my-plan-versions/`、`data/derived/`）。

## 一、这个系统是干什么的

一句话：**把教务发布的课程计划，变成一份"这个人这学期真的能上、且都抢得到"的课表。**

它其实是四个主体拼起来的链条，不是单一系统：

| 主体 | 扮演的角色 | 提供什么 / 缺什么 |
| --- | --- | --- |
| 开课单位 + 教务 | 制定者 | 发布两份开课计划工作簿（校区、学期、课程属性、学分）——**没有开课周、没有星期节次、没有容量** |
| 选课地图类第三方工具 | 转译者 | 把工作簿导入成可查询课程库，提供排课地图、方案导出、本地备份；其内置课程库**有开课周、星期节次、限选、已选**，但**没有校区字段**，且只有一季 |
| 选课系统（官方） | 执行者 | 实际提交选课，**先到先得**，有固定开放窗口 |
| 学生（你） | 唯一的整合者 | 读培养方案、拼数据、判冲突、排优先、抢课、失败后重排——**全部人工** |

关键结构性事实：**没有任何一个主体同时持有"这个人该上什么课"和"这些课什么时候上、还有没有位置"这两组信息。**
前一组（培养方案要求）只存在于文本里，任何数据源都没有；后两组分散在上面几个源里，且各源只覆盖一部分。

## 二、流程（每一步的输入、工具与卡点）

```
1. 读培养方案，确定必须上的课        [人工] 要求不在任何数据源里 → 卡点(1)
2. 收集候选班次 + 时间               [三源手工拼接] 官方无周次/节次 → 卡点(2)
3. 收集每门课的容量与已选            [只有第三方源有] → 卡点(3)
4. 核对时间冲突（星期 ∧ 节次 ∧ 周次）[人工] 唯一带周次的是手排的周表 → 卡点(4)
5. 决定抢课顺序                      [人工] 与"重要性"不是一个序 → 卡点(5)
6. 在窗口内提交                      [选课系统] 先到先得，容量有限 → 卡点(6)
7. 没抢到 / 改主意，回到第 4 步       [全量重做] → 卡点(7)
```

| 步骤 | 谁做 | 输入 | 输出 |
| --- | --- | --- | --- |
| 1 | 学生 | 培养方案文本 | "必修/学位课清单"（存在脑子里） |
| 2 | 学生 | 官方工作簿 + 第三方课程库 | 候选班次清单（手工拼） |
| 3 | 学生 | 第三方课程库 | 每门课的限选/已选 |
| 4 | 学生 | 手排的按周分表课表 | "有没有冲突"的判断 |
| 5 | 学生 | 上一步结果 + 培养方案 | 抢课顺序（存在脑子里） |
| 6 | 选课系统 | 提交 | 选中 / 满员 / 失败 |
| 7 | 学生 | 失败结果 | 重排 → 回到第 4 步 |

## 三、数据地图：三源各自的字段覆盖（实测）

| 字段组 | 官方工作簿（源A/B） | 第三方公开源（源C） |
| --- | --- | --- |
| 开课校区 | 有 | **完全没有该字段**（只能靠课程编码第 18 位 = `Y` 推断） |
| 开课学期 | 有 | 没有 |
| 课程属性、学分 | 有 | 有 |
| 开课周（周次） | **732 条里 0 条** | 347 门里 347 门全有 |
| 星期节次 | **732 条里 0 条** | 347 门里 347 门全有 |
| 限选 / 已选 | **732 条里 0 条** | 347 门里 347 门全有 |
| 培养方案是否要求 | 没有 | 没有 → **只能人工输入** |

官方导入器自己报了 4 条缺陷，都是同一件事：*工作表缺少 培养层次、开课周、星期节次，相关信息可能无法显示或筛选*。

**三源按课程编码联接的结果（这是问题的核心）：**

| | 门数 |
| --- | --- |
| 官方工作簿：玉泉路记录 / 不同课程 | 732 条 / 414 门 |
| 第三方公开源：玉泉路课程（按编码第 18 位 = Y 识别） | 347 门 |
| **两边都有**（全字段齐） | **217 门** |
| **只有官方**（无周次、无节次、无容量） | **197 门** |
| **只有第三方**（无校区、无学期） | **130 门** |

也就是说：**把三源拼起来之后，仍然有 327 门课缺一组关键字段**（197 + 130）。

## 四、痛点清单（每条都可测量）

### PF-1 关键字段分散在三个源里，且三源只部分重叠
- **实测**：217 门两边都有；197 门只有官方、130 门只有第三方；官方 732 条玉泉路记录里，开课周 0 条、星期节次 0 条
- **后果**：想得到一份"能判冲突、能定抢课顺序"的输入，必须人工跨源拼接，且拼完仍不完整
- **谁受影响**：学生（唯一整合者）

### PF-2 冲突判断是三维的，但唯一带周次维度的东西是手排的周表
- **实测**：方案是 19 张按教学周分的工作表（`第2周`…`第20周`，另有一张"全部课程"清单）；周次维度由课出现在哪张表里表达，没有字段
- **后果**：核对冲突等于人眼在 19 张表之间横向比较同一门课
- **谁受影响**：学生

### PF-3 同一个"星期+节次"槽位会被多门周次不重叠的课分时占用
- **实测**：2026-09-05 版方案的 `C5` 槽位（周二第 1–4 节）—— 第 11–18 周是《新时代中国特色社会主义理论与实践》，第 2–5、7–10 周是《自然辩证法概论》
- **后果**：只比较"星期+节次"的检查会**误报冲突**；而只看单张周表的检查会**漏报**只在部分周开的课
- **注**：这是三维判断不可替代的直接证据

### PF-4 容量与竞争信息只在一个源里，而且随时间变，快照还没有时间戳
- **实测**：玉泉路有容量数据的 306 门中，已满 43 门、90–99% 39 门、70–90% 39 门 → **≥90% 满共 82 门（约 27%）**
- **实测**：同一门课在两份快照中已选人数不同（《自然辩证法概论》376/420 与 415/420；《数字信号处理原理与应用二班》111/111 与 106/111），**而两份快照都没记抓取时间**
- **后果**：不冻结时间戳，任何"还剩几个位置"的说法都无法作为依据；也无法判断哪份更新
- **谁受影响**：学生（决定抢课顺序的唯一依据）

### PF-5 "课程重要性"和"抢课顺序"是两个不同的序，而没有任何工具输出这两张清单
- **实测**：《数据挖掘》（学科核心课，重要）已选 1/58（2%），零竞争；而一门 0.5 学分的公共必修课已达 106/111（95%）
- **后果**：按"重要性"排抢课顺序会抢错；必须同时输出①无冲突方案 ②抢课顺序
- **谁受影响**：学生

### PF-6 最紧急的课，正好是最查不清能不能推后的课
- **实测**：方案 14 门里，**6 门在任何数据源里都没有学期记录**；而这 6 门里 **5 门已达 95% 以上容量**
- **后果**：能推后与否无法判断 → 既可能白抢，也可能错过一门一年才开一次的课
- **谁受影响**：学生（风险敞口最大的地方）

### PF-7 每改一次方案，都要把全部班次重新核一遍
- **实测**：两个版本之间 22 个位置被删、45 个位置新增、**0 个位置是原地改文本**；工作表数 21 → 19，非空单元格 901 → 558
- **后果**：方案不是被"修补"，是被整体重排；每次重排都触发一次全量重核
- **谁受影响**：学生

### PF-8 玉泉路 414 门课里，相当一部分一年只有一季开
- **实测**：仅秋季开 208 门、仅春季开 179 门、春秋都开 27 门
- **后果**：本学期不开的课（179 门）根本选不了；只在本学期开的课（208 门）错过要等一年
- **谁受影响**：学生（与培养方案叠加后决定"必须抢"的集合）

### PF-9 "必须上"这条信息不在任何数据源里
- **实测**：四个源（含第三方）都没有"培养方案要求"字段
- **后果**：任何自动化都无法推出必须上哪些课，必须保留一个人工输入口；假装全自动的方案会给出错误建议
- **谁受影响**：工具设计本身（这是一个约束，不是一个可修的 bug）

## 五、为什么会这样（根因链）

1. **官方计划表是"给人看的"**：它是排班结果表，不是数据接口。缺少开课周与星期节次，导入器只能报警而不能补全（实测报了 4 次）。
2. **面向学生的第三方源补上了这些字段，但换了组织方式**：它按"课程"组织并带上开课周/节次/限选/已选，却没有校区字段，只能靠课程编码第 18 位 = `Y` 这条规则来切玉泉路；而且只有一季、快照不带时间戳。
3. **机制本身带时间压力**：先到先得 + 容量有限 + 27% 的课 ≥90% 满 ⇒ "什么时候提交"和"选什么课"一样重要。
4. **培养方案要求是文本**：它决定了"必须上"，但从未被结构化 ⇒ 机器的能力边界在第一步就画好了。

这四条合起来解释了为什么流程第 2–5 步全是人工，也解释了为什么 A1 的"这个麻烦值得一个学期的软件项目"站得住。

## 六、能做的 vs 不能做的

| 可解（工具职责范围） | 不可解 / 明确排除 |
| --- | --- |
| 按课程编码联接三个源并冻结成一份可复现输入 | 自动提交、自动抢课（破坏先到先得、可能违规） |
| 三维冲突判定（星期 ∧ 节次 ∧ 周次，含周次有缺口的情况） | 推断培养方案要求（数据里不存在，必须人工输入） |
| 输出两张清单：无冲突方案 + 抢课顺序 | 读取他人选课记录 |
| 逐条给出排除理由（写出重叠的具体周次区间） | 用猜测数据填补缺失字段 |
| 所有快照带时间戳与哈希 | 保证容量数据永远最新（只能冻结时点） |

## 七、对 A1–A6 的意义

- **A1**：第 2、3 节直接用本文第二、四节；"必须上"与"容易被抢完"两条判据对应 PF-5、PF-6、PF-9
- **A2**：PF-3 是天然的不变式（三维冲突判定），PF-4 是天然的隐私/数据边界（容量快照的时间语义），PF-9 是天然的"人工输入契约"
- **A3**：三源联接与快照冻结已经是可复现的工程问题，正好需要一个陌生仓库来借鉴
- **A4**：垂直切片选"冲突检测 + 抢课顺序"这一刀，PF-1/3/6/7 都是它必须处理的情形
- **A5**：待否证的主张现成——"冲突判定在任何周次组合下都不漏判"，反例就是 PF-3 的 `C5` 情形
- **A6**：代表性负载是选课窗口开放瞬间的并发拉取；可靠性主张是幂等与快照一致性（PF-4）

## 八、还需要补的两件事

1. **"必须上"的清单**：只有你能提供（PF-9）。没有它，抢课顺序只能按课程属性给候选分档。
2. **基线耗时**：现在没有任何"人工核一遍要多久"的实测数字。这是 A1 第 4 节唯一的空格。
